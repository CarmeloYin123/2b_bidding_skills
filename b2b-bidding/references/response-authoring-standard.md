# 响应文件格式与技术方案编写标准

适用于投标文件、谈判响应文件及其技术方案。项目招标文件、补遗、平台规则或采购方指定模板对某一项有明确要求时，以其为准；未明确时，执行本标准。历史案例只能提供结构和版式参考，不能覆盖本标准或项目要求。

## 一、默认版式合同

除采购方明确要求保留的封面、原始表格、扫描件、签章页和附件外，正文、标题、表格文字、页眉页脚均使用**宋体**。不以模板中遗留的仿宋、微软雅黑、Times New Roman 或其他字体作为默认样式。

| 文本角色 | 字体 | 字号 | 对齐 | 缩进 | 段前/段后 | 行距 |
|---|---|---|---|---|---|---|
| 一级标题 | 宋体 | 小二（18 pt） | 左对齐 | 左/右 0；特殊格式：无 | 0 行 / 0 行 | 1.5 倍 |
| 二级标题 | 宋体 | 三号（16 pt） | 左对齐 | 左/右 0；特殊格式：无 | 0 行 / 0 行 | 1.5 倍 |
| 三级标题 | 宋体 | 小三（15 pt） | 左对齐 | 左/右 0；特殊格式：无 | 0 行 / 0 行 | 1.5 倍 |
| 四级标题 | 宋体 | 四号（14 pt） | 左对齐 | 左/右 0；特殊格式：无 | 0 行 / 0 行 | 1.5 倍 |
| 五级标题 | 宋体 | 小四（12 pt） | 左对齐 | 左/右 0；特殊格式：无 | 0 行 / 0 行 | 1.5 倍 |
| 六级标题 | 宋体 | 五号（10.5 pt） | 左对齐 | 左/右 0；特殊格式：无 | 0 行 / 0 行 | 1.5 倍 |
| 正文（含表格正文） | 宋体 | 小四（12 pt） | 两端对齐；从左到右 | 左/右 0；特殊格式：无 | 0 行 / 0 行 | 1.5 倍 |

执行要点：

1. 标题使用真实的 Word 标题样式或与其等价的可导航样式，不用加粗正文、空格或手工编号伪造层级。
2. 标题与正文均不得设置首行缩进、悬挂缩进或负缩进；不要以空行、软回车或多个空格制造间距。
3. 表格内内容默认执行正文样式；采购方提供的不可编辑原表保持原状。若必须保留原表的特殊格式，在工作包记录依据和范围。
4. 保留模板的目录、编号、页眉页脚、分节、表格、图片关系和签章/附件槽位；实施本标准不能破坏采购方格式、模板功能或版式保真。
5. 完成后逐页渲染检查，并在 DOCX 中抽检所有六级标题和正文（含表格、页眉页脚）的字体、字号、对齐、缩进、间距与行距；不得仅凭文本抽取判断合格。

## 二、技术方案资料提取与应答

### 输入和证据边界

技术方案必须同时基于当前招标文件/技术规范和用户提供的产品白皮书、PPT/PPTX、XLSX、DOCX、PDF、架构图或经确认的材料。先完成资料清单和逐项映射，再起草客户正文。

读取 DOCX/PDF 时使用文档/PDF处理能力并逐页渲染核验；读取 PPT/PPTX 时使用演示文稿处理能力，逐页检查文字、备注、图表和图片；读取 XLSX 时使用表格处理能力，逐工作表、表格、图表和关键单元格检查。对 DOCX 批注使用真实 Word 批注机制，不用普通文字模拟批注。

| 状态 | 处理方式 |
|---|---|
| 已有来源直接支撑且适用于当前项目 | 以文件、页码/幻灯片/工作表/单元格定位为证据，写入对客正文 |
| 资料表明能力相关，但无法证明招标条件、范围、性能或交付边界 | 不写成满足承诺；在对应技术响应处添加 Word 批注 |
| 已确认不满足或与招标条件冲突 | 不写成满足承诺；在对应技术响应处添加 Word 批注并升级处理 |
| 资料没有覆盖 | 不编造内容；在对应技术响应处添加 Word 批注 |

每个技术条款至少记录：招标条款定位、拟写章节、来源文件和精确定位、可用事实/图片、满足状态、批注编号和责任人。该映射可写入 `requirements-matrix.md` 与 `evidence-register.md`；不得只保留在对话中。

### 提取、编写和排版顺序

1. **完整读取**：逐页/逐图检查白皮书和 DOCX/PDF，逐页检查 PPT，逐表/工作表/单元格检查 XLSX；提取文本、图表、架构图、流程图、产品截图、关键参数和适用限制。
2. **筛选映射**：仅选择能回应当前技术条款、方案架构、实施、接口、安全、性能、运维、培训或验收要求的事实和图片；标明来源定位及是否可对外使用。
3. **编写对客正文**：将已证实的信息整理为完整、具体、连贯的客户表述，直接说明系统能力、方案组成、处理流程、实施安排和交付边界。不得照抄内部口语、素材标题、测试结论或与本项目无关的产品描述。
4. **图片就近插入**：图片置于其所解释的正文或条款之后，不集中堆放在章节末尾；加入连续图号、简明图题与来源定位。图片须清晰、比例正常、与文本同页或相邻页，并避开页眉页脚、页码、签章区和表格边界。
5. **整体验证**：逐项回链应答矩阵，检查图片所示能力与文字、表格、报价、实施和合同边界一致；渲染后逐页检查图片清晰度、锚点、分页、编号和图文顺序。

### 对客表达和图片控制

1. 仅陈述已由当期资料或已批准项目决策支撑的事实。使用明确、完整的陈述，不使用“可能、预计、原则上、一般情况下、视情况、后续确认、待定、理论上”等模糊措辞。
2. 不把产品白皮书中的功能设想、路线图、演示截图、测试数据或其他客户案例自动写成当前项目能力、交付承诺、性能指标或验收结论。
3. 图片仅从用户授权的当前材料中提取；不得使用带有其他客户名称、联系人、账号、报价、项目数据、未授权标识或敏感界面的图片。必要时先取得替换素材或在内部批注中提出问题。
4. 不得以“满足”“完全响应”“无偏离”替代证据。每一项此类结论必须能回链到招标条款和已核验的资料。

## 三、未满足或待核验技术条件的 Word 批注

在**内部核验版**中，向对应技术应答段落、表格单元格或图片图题添加真实 Word 批注，不把问题写入客户正文。批注必须准确锚定相关条款，使用以下格式：

```text
技术核验提示｜状态：未满足 / 待核验
招标条款：<文件、页码、章节或条款号>
现有资料：<文件、页码/幻灯片/工作表/单元格；无则写“未提供”>
原因：<缺口、冲突或无法证实的具体事实>
需确认/处置：<技术负责人或业务负责人需提供的结论、材料或决策>
责任人：<角色或姓名>；截止：<项目内部截止>
```

- “未满足”仅用于已有证据证明不满足或存在明确冲突的条款；“待核验”用于证据不足、适用性不明或尚未取得批准的条款。
- 不得以高亮、括号提示、隐藏文本、`【待确认】` 或空白替代批注；批注应包含可行动的核验要求。
- 导出对客清洁版前，逐项关闭批注、回填应答矩阵与证据台账，并使用 DOCX 结构检查确认无 Word 批注、批注锚点或未解决技术状态残留。未关闭的批注意味着该版本仅限内部核验，不能标为对客定稿或可递交版本。
